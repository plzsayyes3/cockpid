# iOS native shell for DUO planner — preparation and implementation plan

Date: 2026-11-14
Status: **Xcode project scaffold added; first Xcode/device run pending**
Project: 作業台 (`plzsayyes3/cockpid`); user-supplied device: iPhone Duo; development Mac: M4 MacBook Air.

## Decision

Keep the existing web Workbench as the canonical implementation. Start with a small **SwiftUI + WKWebView native host** reading the live GitHub Pages site; do not rewrite TaskLiner or Daily/Inbox in SwiftUI. Store native source alongside the web project, and use GitHub edit/push → Mac pull → Xcode Run to install native changes on the iPhone. Only if device tests show a meaningful advantage, replace the right-hand planner controls or input features with native SwiftUI or PencilKit components.

## Verified starting point

- Site entry point: `workbench/index.html`; HTML has `viewport-fit=cover`.
- DUO planner spec: `docs/superpowers/specs/2026-11-14-duo-planner-design.md`.
- Existing DUO work/fit plan: `docs/superpowers/plans/2026-11-14-duo-planner-fit.md`.
- Internal TaskLiner: `workbench/taskliner/README.md`, `controller.mjs`; mounted as a reusable Shadow DOM instance, not a duplicate iframe.
- Planner currently separates TaskLiner and right-side Inbox/Daily with width-based 9:1 layout. Right-page edge controls are **within** the Web safe area, not in native OS reserved territory.
- Existing private data remain in `mynotebook` and GitHub; no data-format migration is planned in this phase.

## Phase 1 — native shell smoke test

1. Open the tracked Xcode iOS App project and confirm the two Swift sources are in the target. Do not duplicate `@main`.
2. Configure automatic signing with personal or paid team; set unique bundle identifier.
3. Build/install on iPhone and confirm Home, Duo planner, Tasks and switch/back navigation.
4. Test folded/unfolded widths and both landscape/portrait if supported; measure right OS region, top/bottom safe insets and tappable bands from screenshots.
5. Confirm keyboard focus/IME composition, caret visibility, tap latency and scroll while composing; no double safe-area padding.
6. Test native WKWebView storage separately from Safari/PWA; ensure manual GitHub auth and private Daily/TaskLiner reads, save, conflict handling and Inbox creation work. Start with a deliberate test entry, not bulk data migration.
7. Record screenshots, dimensions, build/Xcode version, the signing mode, and observations in this plan; preserve user data throughout.

## Phase 2 — native value only where validated

- Compare WKWebView against Safari/PWA. Only migrate the right-hand menu to a SwiftUI overlay if there is demonstrable extra usable space or more reliable touch handling; native content cannot override genuinely reserved OS surfaces.
- If a bridge is needed, define a versioned `WKScriptMessageHandler` contract and validate all incoming message types. Do not expose PAT or GitHub API secrets through an unrestricted bridge.
- Evaluate PencilKit for handwriting **after** keyboard and text modes have passed. Keep Markdown, Daily and TaskLiner canonical formats unchanged.
- Decide remote web vs packaged web assets/offline operation based on actual day-to-day reliability.

## Notes / constraints

- This preparation is not a compiled or installed iOS app. The `.xcodeproj` must be created and signed on a Mac running Xcode.
- No App Store/TestFlight distribution is required for initial on-device tests.
- Free Apple Personal Team provisioning has seven-day expiry; paid account may matter for uninterrupted daily use.
- Web-only GitHub pushes become available to native WKWebView on reload, subject to caching; changes to Swift/entitlements/bundle must be rebuilt.
- Keep credentials out of source and documentation. Store a known-safe recovery copy of unsynced drafts before switching surfaces.
- Do not change `workbench/` or delete PWA while building the first host.
